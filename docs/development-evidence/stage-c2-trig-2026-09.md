# Stage C2: binary64 trigonometry (P-008 core)

## Contract

- `sin(x)` / `cos(x)` are Profile 0.12 float intrinsics over binary64
  radians: the operand must be `f64`, the result is `f64`, anything else
  is refused at elaboration (MNE250/MNE251/MNE252), and spelling them
  below Profile 0.12 is refused at parse (MNP201).
- The non-finite trap rule applies at both ends: the operand is guarded
  finite before the libm call and the result is guarded finite after
  it. Any non-finite operand traps (`runtime_failure`), including
  infinities and NaN supplied as corpus bits. Finite results always
  land in `[-1, 1]`, so the post-call guard only fires when the operand
  guard already did.
- Every executable backend reaches the same host libm, so finite
  results agree bit-for-bit, including large magnitudes that stress
  argument reduction (`±1e10`).

## Evidence

- `examples/source/stage-c2-trig.mncs` (6 functions: `fsin`, `fcos`,
  chained `sincos`, nested `sin_of_cos`, identity `pythag`, `main`)
  and `examples/execution/stage-c2-trig-corpus.json` (49 cases,
  generated by `scripts/gen_stage_c2_trig_corpus.py` from an
  independent Python oracle: CPython `math.sin`/`math.cos` call the
  host libm directly, exactly like every MNCS backend).
- 49/49 value agreement on all five executable backends (reference,
  portable WASM, C11, LLVM IR, Cranelift): trap cases assert
  `runtime_failure`, valued cases assert bit-exact agreement
  (including `-0.0`, quadrant coverage, near-multiples of pi, and
  `±1e10` reduction stress).
- Committed test `crates/mncs-cli/tests/stage_c2_trig.rs` runs the
  corpus per backend and requires status plus logical value agreement
  (PASS/UNKNOWN), plus a misuse test asserting the MNP199 arity and
  MNP201 profile-floor diagnostics over
  `examples/source/trig-invalid-arity.mncs` and
  `examples/source/trig-invalid-profile.mncs`.
- Full gate `cargo test --workspace`: EXIT=0 (51 ok suites);
  `cargo fmt` clean; `cargo clippy --workspace --all-targets` clean.

## Latent defects the matrix exposed and fixed

1. The parser accepted `sin`/`cos` inside `intrinsic_selection` but the
   head-position gate (`is_profile08_intrinsic`) never routed there, so
   `sin(x)` parsed as a regular call and died at elaboration (MNE131).
   The gate now admits both names; the Profile 0.12 floor is still
   enforced inside with MNP201 (`crates/mncs-syntax/src/source.rs`).
2. A second `AstExpr` match (`calls_in_expr`) did not cover the new
   `FloatIntrinsic` node (E0004): it recurses into the operand, which
   carries no callees (`crates/mncs-compiler/src/frontend.rs`).
3. Cranelift had no `FloatIntrinsic` lowering: new builder arm (operand
   and result finiteness guards into the shared `fail` block, call
   through a declared `(f64) -> f64` import), disassembly text arm,
   `scalar_dest` coverage, JIT symbols (`sin`/`cos` registered to
   same-process libm shims only when the module uses trig), and `-lm`
   on the AOT link line alongside the existing C11 entry
   (`crates/mncs-codegen/src/cranelift_backend.rs`,
   `crates/mncs-codegen/src/native.rs`).
4. Reproduced-first: non-finite operands reported `invalid_request` on
   WASM but `runtime_failure` everywhere else. The WASM argument
   marshaller fail-closed non-finite float bits at the boundary while
   every other backend passes bits through to the lowering-time
   operand guard. The marshaller now passes bits through (the
   `is_supported` type check stays); the guard produces the uniform
   `runtime_failure` (`crates/mncs-codegen/src/wasm.rs`). Finiteness
   stays a runtime trap, never a request rejection.

## Pressure resolution

- P-008 trig: RESOLVED for `sin`/`cos` over binary64 on all five
  executable backends with a bounded corpus and a committed
  per-backend test. Remaining trig surface (further libm functions,
  if any are pressured) is new work, not a gap in this contract.
- P-001 float semantics: RESOLVED with C1 + C2 combined (scalar type,
  arithmetic, comparisons, conversions, trap rule, trig, backend
  facts, bounded corpora).
