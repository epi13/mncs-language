# Standard-library bundle distribution (INGEST-P-008)

Filesystem roots (`MNCS_LIBRARY_PATH`) remain the development mechanism
for resolving `mncs.*` imports. The bundle is the distribution mechanism:
a content-addressed document that lets a downstream in-process consumer
resolve a pinned `mncs.std.*` identity without depending on the
`mncs-language` working-tree path and without copying the library into
its own repository.

## The pin

`library/stdlib-bundle.json` is the checked-in pin, generated by
`mncs bundle generate` from `library/`:

- one entry per distributable (`mncs.*`) module: declared name, library
  path, declared profile, `sha256` over the exact source bytes, and the
  full source text;
- `bundle_identity` is `mncs:stdlib-bundle:{hex}` over the sorted
  `(name, content_sha256)` pairs: the pin names content, never a path, a
  timestamp, or a branch.

Regenerating from an unchanged tree reproduces the identity byte for
byte. A stdlib edit without re-pinning fails the freshness test
(`mncs-compiler/tests/stdlib_bundle.rs`) instead of drifting downstream.

## Commands

- `mncs bundle generate --library DIR --output FILE [--commit HASH]`
  collects every `mncs.*` module under `DIR` (declared names and profiles
  come from the same inference the source envelope uses) and writes the
  sealed document.
- `mncs bundle verify FILE` re-verifies every content hash and the bundle
  identity, failing closed on any drift.

## Resolution

`MNCS_STDLIB_BUNDLE` names a bundle file for any resolving command
(`source-study`, `experiment`, `conformance`, ...). The bundle joins the
existing authority set under the existing rules
(HARNESS-PRESSURE-008):

- byte-identical content from the pin and a filesystem root collapses to
  one authority — re-pinning a tree you already resolve is silent;
- divergent content for one identity fails closed as `MNE234`, naming
  both locators including the `stdlib-bundle:{pin}:{module}` locator. The
  pin never silently shadows a working tree, and a working tree never
  silently shadows the pin. Divergence means "re-pin", and it says so.
- only exact versioned names match the bundle (`mncs.std.chunk.v1`);
  unversioned requests (`mncs.std.chunk`) keep flowing to the filesystem,
  which preserves the development workflow: the tree wins until the
  request names a pin.
- an unreadable or unverifiable bundle fails the invocation loudly; an
  unset variable means pure filesystem resolution, exactly as before.

Bundle envelopes carry a `Generated` origin naming pin and module, so the
P-007 import-failure chain identifies which pin served a failing module.

## In-process adoption

`mncs-compiler::bundle` exposes `StdlibBundle::from_json`,
`StdlibBundle::resolver` (a plain `ModuleResolver` for any
`ReferenceCompiler` consumer), and `pinned_bundle()` over the
`PINNED_STDLIB_BUNDLE_JSON` text embedded in the crate — resolution with
no path at all:

```rust
let bundle = mncs_compiler::bundle::pinned_bundle().expect("stdlib pin");
let front_end = compiler.front_end_with_resolver(envelope, &bundle.resolver());
```

A consumer that vendors stdlib sources today (for example through a
`vendor/` directory consulted by its own resolver) migrates by offering
the bundle as one more authority and deleting the vendored copies once
the pin resolves the same modules. Byte-identical vendored copies already
collapse under the authority rule, so the migration is observable step by
step rather than flag-day.

## Non-goals

This is not a package manager: no registry, no network fetch, no version
constraint solving, no third-party namespaces. The bundle distributes the
first-party `mncs.*` tree as content-addressed bytes; anything beyond
that waits for a real requirement.
