# Machine-Intent Expressions 0.1 Direction

This document states experimental semantic requirements derived from
[RFC 0006](../rfcs/0006-machine-intent-expressions.md). The Rust model implements only a narrow
pilot: integer addition intents, distinct fact/preference/requirement/obligation records,
PASS/FAIL/UNKNOWN handling, an identity-bound alignment capability, intent-preserving high-level
IR records, and a conservative no-overflow promise decision. No surface grammar is selected.

## 1. Purpose

A machine-intent expression makes machine-oriented behavior explicit without making source-level
accidents, undefined behavior, compiler folklore, or backend-specific intrinsics authoritative.

Every supported expression identifies:

- exact value and failure semantics;
- declared effects and required capabilities;
- machine intent and optional preferences;
- established facts consumed by lowering;
- requirements that every accepted realization must preserve;
- generated obligations;
- permitted lowering choices;
- target and portability limits;
- reference semantics when applicable; and
- evidence and invalidation rules.

Machine intent MAY guide verified implementation selection. It MUST NOT weaken declared semantics,
satisfy a requirement by itself, or convert unsupported evidence into `PASS`.

## 2. Semantic categories

The semantic graph MUST distinguish the following categories.

### 2.1 Operation

An operation defines stable value, state, effect, failure, and edge-case behavior.

### 2.2 Intent

Intent explains why a machine property is useful. Intent is descriptive and does not establish that
the property was achieved.

### 2.3 Preference

A preference guides candidate ordering or cost selection. A compiler MAY ignore a preference while
preserving semantics.

### 2.4 Fact

A fact is a proposition established for an exact subject and scope by:

- a language construction rule;
- static analysis or proof;
- an explicit runtime check;
- a verifier result; or
- another evidence-bearing capability.

A fact MUST identify its basis and invalidation dependencies.

### 2.5 Requirement

A requirement is part of the expression's semantic contract. Every accepted realization MUST
preserve it.

### 2.6 Obligation

An obligation is a stable, named proposition generated by an expression or lowering rule. It has
`PASS`, `FAIL`, or `UNKNOWN` status under a declared method and scope.

### 2.7 Lowering envelope

A lowering envelope enumerates permitted transformation classes and realizations. It does not grant
permission to change the operation's declared semantics.

### 2.8 Portability envelope

A portability envelope identifies the targets, features, data layouts, ABIs, compiler/backend
semantics, runtime conditions, and fallback behavior for which a selected realization applies.

## 3. Required graph shape

A machine-intent expression SHOULD be representable by the following conceptual graph:

```text
expression
 ├─ operation
 ├─ operands
 ├─ result type
 ├─ effects
 ├─ required capabilities
 ├─ intent
 ├─ preferences
 ├─ established facts
 ├─ requirements
 ├─ lowering envelope
 ├─ portability envelope
 ├─ reference semantics
 ├─ generated obligations
 └─ evidence policy
```

Each edge MUST contribute to semantic identity when changing it could change meaning, permitted
lowering, evidence sufficiency, or portability.

## 4. Arithmetic operations

The initial arithmetic family SHOULD include:

```text
add.wrap<T>
add.checked<T>
add.saturate<T>
add.trap<T>
sub.wrap<T>
sub.checked<T>
mul.wrap<T>
mul.checked<T>
mul.widen<T, Wide>
convert.exact<From, To>
convert.saturate<From, To>
shift.checked<T>
shift.masked<T>
rotate.left<T>
rotate.right<T>
```

### 4.1 Wrapping

Wrapping arithmetic MUST use modulo-`2^N` semantics for an `N`-bit integer type. It MUST NOT be
implemented by relying on signed-overflow undefined behavior in a backend language.

### 4.2 Checked

Checked arithmetic MUST expose overflow through the declared result or failure model. An optimizer
MUST NOT remove the overflow result unless a current fact proves overflow impossible.

### 4.3 Saturating

Saturating arithmetic MUST clamp to the destination type's declared minimum or maximum.

### 4.4 Trapping

Trapping arithmetic MUST follow a declared failure path. The trap behavior, recoverability, and
observable effects MUST be explicit.

### 4.5 Widening

A widening operation MUST compute in a result domain that represents the full declared operand
domain or else expose the remaining overflow behavior explicitly.

## 5. Floating-point policy

Floating-point relaxation MUST be decomposed into explicit properties. A policy MAY address:

- rounding mode;
- NaN behavior;
- infinity behavior;
- signed-zero behavior;
- reassociation;
- contraction or fused operations;
- reduction order;
- denormal handling;
- exception behavior; and
- bounded error metric.

A backend MUST NOT enable a relaxation that is absent from the expression policy merely because
another relaxation is present.

## 6. Evidence-bearing memory capabilities

Memory operations MAY require capabilities such as:

```text
Aligned<Subject, N>
InBounds<Allocation, Range>
Disjoint<RegionA, RegionB>
Live<Allocation, Epoch>
Provenance<Pointer, Allocation>
Exclusive<Region, Scope>
```

A capability MUST bind:

- property identity;
- exact subject identities;
- scope or lifetime;
- construction or verifier identity;
- assumptions;
- dependency identities; and
- invalidation triggers.

A capability for one allocation, region, target, epoch, or candidate MUST NOT satisfy an obligation
for another.

## 7. Closed computed dispatch

A closed dispatch operation MUST identify:

- selector and selector domain;
- immutable target-set identity;
- target signatures and calling convention;
- default or invalid-selector behavior; and
- required authority and effects for each target.

It MUST generate obligations covering at least:

```text
selector_within_domain
target_set_closed
target_table_immutable
target_signatures_compatible
target_address_not_untrusted
control_entry_declared
```

Permitted realizations MAY include jump tables, decision trees, conditional sequences, predicated
forms, or target-specific indirect branches.

## 8. Branchless and constant-time operations

Branchless lowering and constant-time behavior MUST remain separate concepts.

A branchless expression MAY state a preference or requirement concerning control-flow shape.

A constant-time expression MUST identify:

- secret inputs or labels;
- target timing-model identity;
- prohibited secret-dependent control flow;
- prohibited secret-dependent memory access;
- prohibited variable-latency operations; and
- known exclusions or limitations.

Source structure alone MUST NOT establish constant-time behavior. Evidence SHOULD inspect an
appropriate optimized IR, machine artifact, or runtime model.

## 9. Logical types and physical layouts

The semantic system MAY separate logical value identity from physical storage layout.

A layout realization MUST preserve:

- logical field and value semantics;
- ownership and borrowing relations;
- alignment and bounds;
- declared serialization and FFI behavior;
- effect and authority boundaries; and
- reference equality or ordering where defined.

Performance evidence MAY guide layout selection only after semantic obligations pass.

## 10. Target-specialized realizations

A semantic operation MAY have multiple target realizations and a portable fallback.

Every realization MUST share the same operation identity and requirements. A selected realization
MUST bind:

- architecture and feature set;
- data layout, pointer width, and endianness where relevant;
- ABI and calling convention;
- compiler/backend identity;
- optimization-pipeline identity;
- runtime dispatch policy; and
- fallback or unsupported behavior.

A target mismatch MUST cause explicit fallback, rejection, or `UNKNOWN` according to policy. It MUST
NOT silently change semantics.

## 11. Security-bound values and authority

The type and capability system MAY represent bounded security states such as:

```text
Untrusted<T>
Secret<T>
Authenticated<Principal>
Authorized<Principal, Resource, Operation>
ConfinedPath<Root>
```

Operations SHOULD consume the narrowest capability sufficient for their effect. A capability MAY be
single-use, affine, linear, scoped, or persistent according to the authority it represents.

Intent or comments MUST NOT substitute for an authorization, confinement, or validation capability.

## 12. Reference semantics

An operation MAY bind one or more optimized realizations to reference semantics.

The reference MAY be:

- an executable implementation;
- a relational contract;
- a mathematical definition;
- a state-transition system; or
- another versioned semantic operation.

The reference's own assumptions and evidence boundary MUST remain explicit. Simplicity does not make
a reference automatically correct or independent.

## 13. Optimization regions

A bounded optimization region MUST identify:

- semantic reference or protected relation;
- candidate mutation scope;
- required properties;
- permitted authority and effects;
- target envelope;
- resource budget;
- candidate and verifier-call limits;
- objective metrics;
- deterministic comparison or tie-breaking policy;
- required independent evidence; and
- promotion authority.

Candidate generation MUST create an isolated candidate identity. It MUST NOT modify the trusted
baseline directly or promote its own evidence.

## 14. Obligation status and fallback

Obligation handling MUST follow:

- `PASS` permits only dependent lowering choices within the verifier's declared scope;
- `FAIL` rejects dependent choices and may reject the expression when no fallback exists;
- `UNKNOWN` prevents dependent promises but MAY permit a declared conservative fallback.

The compiler MUST NOT silently treat `UNKNOWN` as `PASS`.

A workflow disposition such as `accepted_with_constraints` or `review_required` MUST remain separate
from obligation status.

## 15. Lowering order

An implementation SHOULD lower in this order:

```text
source representation
    ↓
canonical semantic operation
    ↓
obligation instantiation
    ↓
static discharge, runtime-check insertion, or verifier request
    ↓
valid realization set
    ↓
policy and preference selection
    ↓
high-level MNCS IR
    ↓
verified SSA
    ↓
backend IR and artifact
    ↓
evidence manifest
```

A realization MUST NOT enter the valid set until every required prerequisite is accounted for.

## 16. Intent-preserving IR

High-level MNCS IR MUST preserve operation and obligation identity. Illustrative operations are:

```text
mncs.add.wrap.i32
mncs.add.checked.i32
mncs.reduce.sum.f32 policy_ref
mncs.load.aligned.u32 alignment_cap bounds_cap
mncs.dispatch.closed target_set_ref
mncs.select.constant_time timing_model_ref
mncs.layout.realize logical_type_ref layout_ref
mncs.authorization.consume authority_cap
```

Verified SSA MAY lower these to ordinary instructions and blocks only while retaining traceability
to:

- source and semantic identities;
- consumed facts and capabilities;
- generated runtime checks;
- transformation rules;
- discharged obligations;
- target profile; and
- evidence records.

Semantically required intent MUST NOT survive only as discardable debugging metadata.

## 17. Backend promises

Backend attributes and flags are semantic promises. A compiler MUST emit a promise only when:

1. the semantic operation permits it;
2. the exact required obligations pass;
3. consumed evidence is current;
4. the backend interpretation is known for the selected version; and
5. the transformation record identifies the basis.

This requirement applies to promises such as:

- no signed or unsigned overflow;
- in-bounds pointer arithmetic;
- non-aliasing;
- non-null and dereferenceability;
- alignment;
- floating-point relaxation; and
- reduced atomic ordering.

When proof is absent, the compiler MUST use conservative semantics or report unsupported behavior.

## 18. Evidence record

A lowering evidence record SHOULD identify:

```text
expression_identity
operation_identity
reference_identity
realization_identity
obligation_identities_and_results
capability_identities
source_semantic_ir_ssa_artifact_identities
target_profile
compiler_backend_pass_identities
verifier_identities
assumptions
limitations
dependency_envelope
resource_measurements
status
freshness
```

A change to any material identity MUST invalidate dependent evidence unless a complete dependency
argument establishes that the result remains current.

## 19. Diagnostics

A failed obligation SHOULD produce a stable diagnostic object containing:

- expression and operation identities;
- failed or unresolved obligation;
- evidence status;
- assumptions and limitations;
- smallest defensible causal slice;
- dependent lowering choices or backend promises;
- available conservative fallback; and
- bounded repair region.

A diagnostic MUST NOT claim that absence of a demonstrated exploit or failure trace proves the
property.

## 20. Discovery and graduation

A recurring non-orthodox technique SHOULD graduate only when its full semantic pattern is retained:

```text
purpose
+ exact semantics
+ invariants
+ capabilities
+ target envelope
+ lowering alternatives
+ failure behavior
+ evidence and invalidation
```

The language MUST NOT standardize only a source idiom, compiler accident, or instruction sequence.

## 21. Prohibited foundations

A standardized machine-intent expression MUST NOT depend for its semantics on:

- undefined behavior;
- an undocumented compiler bug;
- unspecified optimizer behavior;
- an unversioned target timing assumption;
- a hidden mutable global condition;
- an unchecked broad assertion; or
- evidence that cannot be tied to the selected artifact and environment.

If another language leaves useful behavior undefined, MNCS MUST define that behavior explicitly or
reject the realization.

## 22. Initial implementation subset

The first executable subset SHOULD be limited to:

1. wrapping, checked, saturating, trapping, and widening integer arithmetic;
2. explicit fact, preference, requirement, and obligation objects;
3. one evidence-bearing bounds or alignment capability;
4. deterministic canonical serialization;
5. high-level IR preservation of operation and obligation identities; and
6. one conservative backend-promise experiment.

Constant-time, layout search, lock-free progress, and target-dispatch claims SHOULD remain later
pilots until their trust models and verifier requirements are explicit.
